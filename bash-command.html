⌨️ What Actually Happens When You Type a Command into Bash?

You type:

ls

You press Enter.

Your files appear.

Seems simple.

But underneath that one command, Linux has to do quite a lot.

The shell has to:

  1. Read what you typed.
  2. Work out what you mean.
  3. Find the program.
  4. Create a process.
  5. Start the program.
  6. Give it access to input/output.
  7. Wait for it to finish.
  8. Collect its exit status.

And that's just:

ls

Add a pipe:

ls | grep ".txt"

and things get considerably more interesting.

🧠 The short answer

When you type a command into Bash, the basic process looks something like:

You type command
       │
       ▼
     Bash
       │
       ▼
Parse command
       │
       ▼
Find program
       │
       ▼
   fork()
       │
       ▼
   Child process
       │
       ▼
   exec()
       │
       ▼
Program runs
       │
       ▼
   exit()
       │
       ▼
Bash calls wait()

There are plenty of details hidden inside that diagram, but that's the basic idea.

Let's take it apart.

1️⃣ You type something

Suppose you type:

ls -l

Your keyboard isn't directly talking to ls.

The characters go through your terminal and eventually become input available to the shell.

Bash is the program currently interpreting your commands.

You can check which shell you're using with:

echo $SHELL

On many Linux systems, you'll see something like:

/bin/bash

2️⃣ Bash reads the command

Bash receives:

ls -l

It doesn't immediately execute the text as one giant blob.

It has to parse it.

Parsing means figuring out the structure of the command.

For:

ls -l

Bash can break it into roughly:

command:
    ls

argument:
    -l

But Bash has to handle much more complicated syntax too.

For example:

ls -l > files.txt

Now Bash needs to understand:

command → ls
argument → -l
redirect stdout → files.txt

Or:

ls | grep txt

Now there are two commands:

ls
 │
 │ pipe
 ▼
grep txt

The shell is responsible for setting all of that up.

3️⃣ Bash checks whether it's a built-in

Here's an important detail.

Not every command you type is a separate program.

Bash has built-in commands.

For example:

cd

is a shell builtin.

Try:

type cd

You might get:

cd is a shell builtin

But:

type ls

will usually point to an executable somewhere on your system.

For example:

ls is /usr/bin/ls

This distinction matters.

🤔 Why is cd built into Bash?

Because cd needs to change the current working directory of the shell itself.

Imagine Bash did this:

Bash
 │
 └── child process
       │
       └── cd /home

The child could change its directory.

But when it exits:

Bash
 │
 └── still in old directory

That wouldn't be useful.

So Bash handles cd itself.

This is also why commands such as:

cd
export
alias
unset

are commonly shell builtins.

4️⃣ Bash searches for the program

Suppose you type:

ls

Where is ls?

Bash uses an environment variable called:

PATH

Try:

echo $PATH

You'll probably see something vaguely like:

/usr/local/bin:/usr/bin:/bin:/usr/local/sbin:/usr/sbin

The : separates directories.

Bash searches these directories for executable programs.

So it might effectively check:

/usr/local/bin/ls
/usr/bin/ls
/bin/ls
...

until it finds an appropriate executable.

You can see the location with:

which ls

or, more specifically for Bash:

type -a ls

🧩 PATH is just a list

PATH isn't some magical database.

It's essentially a list of directories.

For example:

PATH=/a:/b:/c

means:

/a
/b
/c

When you type:

program

the shell searches those locations for:

/a/program
/b/program
/c/program

If it finds an executable, that's what it can run.

This is why typing:

program

can work even though you didn't type:

/usr/local/bin/program

5️⃣ Bash creates a process

Now we're getting into the fun stuff.

Suppose ls isn't a Bash builtin.

Bash needs to run another program.

It generally creates a child process.

A traditional Unix/Linux mechanism for this is:

fork()

Conceptually:

Before fork():

Bash

After:

        Bash
       /    \
    Bash     Child

The child is initially very similar to the parent.

It has its own process identity, but it inherits a lot of the parent's process state, including things such as open file descriptors.

6️⃣ The child becomes ls

Here's the really cool part.

The child process doesn't need to remain Bash.

It can replace its program image with another program using:

exec()

There are actually several exec*() functions, collectively called the exec family.

Conceptually:

Child process
     │
     │ exec()
     ▼
    /usr/bin/ls

The process itself continues with the same PID, but its running program is replaced.

So:

Bash
 │
 └── PID 420
      │
      └── Bash code

becomes:

Bash
 │
 └── PID 420
      │
      └── ls code

The PID stays the same.

The program being executed changes.

🤯 fork() + exec() is everywhere

A simplified version of running an external command is:

Bash
 │
 ├── fork()
 │
 └── child
       │
       └── exec("/usr/bin/ls")
                    │
                    ▼
                   ls

This pattern is fundamental to Unix-like operating systems.

It also explains why our zombie article mattered.

When ls finishes:

ls
 │
 └── exit()

Bash can collect the result with:

wait()

So our previous articles are starting to connect.

7️⃣ What about the output?

Remember file descriptors?

A process normally starts with:

0 → stdin
1 → stdout
2 → stderr

When Bash launches ls, those descriptors can be inherited by the child.

So:

Bash
 │
 ├── stdout → terminal
 │
 └── fork()
       │
       └── ls
            │
            └── stdout → terminal

That's why ls can simply write to stdout and the output appears in your terminal.

8️⃣ Redirection changes everything

Now type:

ls > files.txt

Bash sees the >.

It knows this means:

Send standard output somewhere else.

Conceptually, Bash sets up:

ls
 │
 │ stdout
 ▼
files.txt

instead of:

ls
 │
 │ stdout
 ▼
terminal

The ls program doesn't need special knowledge about the shell syntax.

As far as ls is concerned, it just writes to:

stdout

Bash changed what stdout points to.

This is one of the reasons file descriptors are so powerful.

🔀 9️⃣ Now add a pipe

Consider:

ls | grep txt

Bash has to create two processes:

        Bash
       /    \
      ls    grep
       │      ▲
       │      │
       └ PIPE ┘

More accurately:

ls
 │
 │ stdout
 ▼
┌─────────┐
│  PIPE   │
└─────────┘
 │
 │ stdin
 ▼
grep txt

Bash creates the pipe and connects the processes to its two ends.

Then:

ls

writes into the pipe.

And:

grep

reads from it.

🧠 Bash is basically an orchestra conductor

This is where the shell becomes really interesting.

Bash isn't necessarily doing the actual work of:

ls
grep
sort
wc
python

Instead, it's coordinating them.

It says, roughly:

“Run this.”
“Give it this input.”
“Send its output here.”
“Connect these two programs.”
“Run this one in the background.”
“Wait for these processes.”
“Tell me when they're finished.”

The kernel then provides the underlying mechanisms.

🔟 The program runs

Eventually the child has become ls:

PID 420
/usr/bin/ls

The CPU starts executing its instructions.

ls:

  • looks at the current directory
  • obtains information about entries
  • formats the output
  • writes the result to stdout

Eventually it finishes.

1️⃣1️⃣ The process exits

When ls is finished, it exits.

Conceptually:

ls
 │
 └── exit(0)

The 0 means successful completion in the conventional Unix sense.

Bash needs to know the result.

So it waits for the child:

Bash
 │
 └── wait()
       │
       ▼
   exit status

Then Bash can show you another prompt:

tux@linux:~$

The whole cycle is complete.

🧪 You can see some of this yourself

Run:

type ls

Then:

type cd

You'll see that they're different kinds of commands.

Now:

which ls

This should give the path to the executable.

Then:

echo $PATH

to see where Bash searches.

You can also inspect the process tree:

pstree

While a program is running, another terminal can show its processes with:

ps

🐌 What about a slow command?

Try something harmless like:

sleep 10

While it's running, open another terminal and use:

ps

You should be able to find the sleep process.

You can also see its PID and parent PID with:

ps -o pid,ppid,state,cmd

You might see something like:

PID   PPID   S CMD
420    100   S sleep 10

So:

PPID 100
   │
   └── PID 420
        └── sleep 10

Once the ten seconds are over, the process exits.

⚙️ What the kernel actually does

Bash can't simply tell the CPU:

“Hey, run /usr/bin/ls.”

There is a boundary between ordinary programs and the kernel.

Programs request operating-system services using system calls.

The exact sequence varies depending on the shell, implementation, platform, and command, but conceptually you can think of:

Bash
 │
 │ system calls
 ▼
Kernel
 │
 ├── create/manage process
 ├── open files
 ├── set up pipes
 ├── manage memory
 ├── access filesystem
 └── schedule CPU time

The kernel is ultimately responsible for controlling access to the hardware and system resources.

/proc/<PID>

stdin

Now put them together:

             Bash
              │
           fork()
              │
              ▼
          Child process
              │
           exec()
              │
              ▼
           Program
              │
       ┌──────┴──────┐

That's a surprisingly large amount of operating-system theory hiding behind:

ls

🤯 The weird bit

Here's the part that tends to break people's brains:

When Bash runs an external program, the process doesn't necessarily disappear and get replaced by another process.

Instead, you can have:

Bash
 │
 └── child PID 420

and then PID 420 does:

exec()

Now PID 420 is running an entirely different program.

So:

PID 420
   │
   ├── Bash? ❌
   │
   └── ls? ✅

Same process identity.

Different program image.

That's what makes exec() so interesting.

🧟 And remember the zombies

If the child finishes:

Child
  │
  └── exit()

but Bash doesn't collect its status:

Bash
 │
 └── Zombie

So the zombie from Article #4 wasn't some completely separate phenomenon.

It can literally be the final stage of the process you just watched Bash create.

🕳️ Rabbit hole →

If you want to go deeper, there are several directions.

fork() under the microscope

How can a process apparently duplicate itself? And why doesn't Linux literally copy every byte of memory immediately? Hint: copy-on-write.

execve()

The real system call underneath the exec family. It loads a new executable and its environment into the process.

ELF

Linux executables are commonly stored using the Executable and Linkable Format. That's what lies underneath many files such as /usr/bin/ls and /usr/bin/bash.

Dynamic linking

ls doesn't necessarily contain every library function it needs. Linux can load shared libraries such as libc.so into memory.

So running one command can involve:

Bash ➔ fork ➔ exec ➔ ELF loader ➔ shared libraries ➔ program

Environment variables

Things like PATH, HOME, USER, and SHELL are passed into programs through their environment. Try env.

Shebangs

Why does ./script.py work when the file isn't itself a machine-code executable? Because of #!/usr/bin/python3. The kernel uses the shebang to determine which interpreter should execute the script.

📝 TL;DR

When you type ls, Bash roughly does this:

You ➔ type "ls" ➔ Bash ➔ parse command ➔ find executable using PATH ➔ fork() ➔ Child ➔ set up input/output ➔ exec() ➔ ls (does work) ➔ exit() ➔ Bash waits ➔ prompt returns

And when you type ls | grep txt, Bash has to coordinate multiple processes and a pipe:

ls ➔ PIPE ➔ grep

So the next time you type a command and instantly get an answer, remember: Bash just orchestrated a tiny process-management operation involving the kernel, processes, file descriptors, and probably several system calls.

All so you could see a list of files.

Linux is normal.
